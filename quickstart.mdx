---
title: "Get started with the Synapse IAP Terraform Providers"
description: "Configure a GCP IAP tunnel Terraform provider and deploy your first resource through a tinyproxy bastion host in under five minutes."
---

This quickstart walks you through adding one of the Synapse Terraform Providers to an existing Terraform configuration. You will configure a provider block, declare an IAP tunnel resource, pass the resulting proxy URL to a downstream provider, and run `terraform apply` — all without setting up any long-lived tunnels outside of Terraform.

## Prerequisites

Before you begin, make sure you have the following:

- A GCP project with [Identity-Aware Proxy](https://cloud.google.com/iap) enabled.
- A GCP Compute Engine instance (bastion host) reachable via IAP, with [tinyproxy](https://tinyproxy.github.io/) running on port `8888`.
- A GCP service account with the `roles/iap.tunnelResourceAccessor` IAM role on the bastion host.
- Terraform `>= 0.13` installed locally, with [application default credentials](https://cloud.google.com/docs/authentication/application-default-credentials) configured.

<Steps>
  <Step title="Configure the provider block">
    Declare the `iap` provider in your `required_providers` block and configure the Google authentication context. The IAP provider inherits credentials from the Google provider.

    ```hcl main.tf
    terraform {
      required_providers {
        iap = {
          version = "~> 1.0.0"
          source  = "example-iap.com/provider/iap"
        }
      }
    }

    provider "iap" {
    }
    ```

    The provider block intentionally has no arguments — authentication is handled by the ambient Google credentials. Set `GOOGLE_APPLICATION_CREDENTIALS` or run `gcloud auth application-default login` before calling `terraform apply`.
  </Step>

  <Step title="Create the tunnel proxy resource">
    Add an `iap_tunnel_proxy` resource. It opens an IAP tunnel to your bastion host and forwards traffic through tinyproxy. Terraform assigns a random free local port at plan time.

    ```hcl main.tf
    resource "iap_tunnel_proxy" "tunnel_proxy" {
      project    = var.project
      zone       = var.zone
      instance   = var.instance
      interface  = var.interface
      remote_port = var.remote_port
    }

    output "tunnel_proxy" {
      value = resource.iap_tunnel_proxy.tunnel_proxy.proxy_url
    }
    ```

    The computed `proxy_url` attribute is populated after the tunnel starts and contains a `http://localhost:<port>` address you can pass to any downstream resource.

    <Note>
      The default value for `remote_port` is `8888`, which is the tinyproxy default. You only need to set this variable if tinyproxy is listening on a different port on your bastion host.
    </Note>

    Declare the corresponding variables in `variables.tf`:

    ```hcl variables.tf
    variable "project" {
      type        = string
      description = "The project of the bastion proxy"
    }

    variable "zone" {
      type        = string
      description = "The zone of the bastion proxy"
    }

    variable "instance" {
      type        = string
      description = "The instance to use for the bastion proxy"
    }

    variable "interface" {
      type        = string
      description = "The interface to use for the bastion proxy"
      default     = "nic0"
    }

    variable "remote_port" {
      type        = string
      description = "The remote_port of the bastion proxy"
      default     = 8888
    }
    ```
  </Step>

  <Step title="Pass the proxy URL to a downstream provider">
    Reference `resource.iap_tunnel_proxy.tunnel_proxy.proxy_url` in any provider that accepts a `proxy_url` argument. The example below routes Kubernetes API calls through the tunnel:

    ```hcl main.tf
    provider "kubernetes" {
      host        = ""
      token       = data.google_service_account_access_token.kube_sa.access_token
      proxy_url   = resource.iap_tunnel_proxy.tunnel_proxy.proxy_url
      config_path    = var.config_path
      config_context = var.config_context
    }

    # Verify the tunnel by fetching a storage class — this will error with a
    # permission or not-found error, which confirms the proxy is working.
    data "kubernetes_storage_class" "example" {
      metadata {
        name = "terraform-example"
      }

      depends_on = [resource.iap_tunnel_proxy.tunnel_proxy]
    }
    ```

    <Warning>
      The IAP tunnel is started and stopped within the provider lifecycle. It is active only for the duration of `terraform apply` or `terraform plan`. Do not share the `proxy_url` value with long-running processes or other Terraform workspaces — the port will not be available after the apply completes.
    </Warning>

    If you are deploying Helm charts instead of Kubernetes resources, use the `helmproxy` provider, which bundles the tunnel and Helm provider together:

    ```hcl main.tf
    provider "helmproxy" {
      instance    = var.instance
      zone        = var.zone
      interface   = var.interface
      project     = var.project
      remote_port = var.remote_port

      kubernetes {
        host           = ""
        token          = data.google_service_account_access_token.kube_sa.access_token
        config_path    = var.config_path
        config_context = var.config_context
      }
    }

    resource "helmproxy_release" "omnirpc_example" {
      name  = "omnirpc-example"
      chart = "../../../charts/omnirpc/"
    }
    ```
  </Step>

  <Step title="Run terraform apply">
    Initialize the workspace and apply:

    ```bash
    terraform init
    terraform apply
    ```

    During the `apply`, the provider starts the IAP tunnel and waits up to 5 seconds for any startup errors before proceeding. If the tunnel fails to start within that window, the provider returns an error and the apply stops.

    After the apply completes, the tunnel is torn down automatically. No background processes remain.
  </Step>
</Steps>
